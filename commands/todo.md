The block above is the live output of the task tracker.

Each task is colour-coded by category (an `<emoji> [TAG]` after the title — the emoji dot carries the colour, the tag names it). When categorising a task, always pick the **most accurate** category from the full taxonomy (`$CLAUDE_PLUGIN_ROOT/CATEGORIES.md`) even if it isn't on the board yet: the board starts lean (just **CORE** — BUG · FEATURE · GENERAL) and a slot is **enabled automatically** the first time a task is assigned to it (unless `config --auto-categories off`). Each category ships a full **Sands** palette that the hooks apply to your terminal automatically via standard escape sequences (zero-setup; iTerm2 and Terminal.app both honored); customize colours without touching that file via `task-station-data/categories.json`.

A task's lifecycle is **one field, `status`, with three values: open (`○`) → active (`●`) → closed (`✕`)**. Each row carries a leading **STATUS column** (before `#`) holding the lifecycle glyph — `○` **open** (a topic merely raised), `●` **active** (work has actually started), or `✕` **closed** (closed rows live in their own section). A task auto-promotes `○ open → ● active` when you delegate `--worktree` for it, edit a file in an attached session, or set it manually with `status --task <ref> active`. New tasks start `○ open` (or `● active` via `create --active`); `/done` closes them (`✕`), and reopening a closed task returns it to `○ open`. The legend under the tables reads `● active · ○ open · ✕ closed`.

- If the output starts with **`[BOARD]`** (`/todo board`), the tracker wrote the self-contained HTML board and tried to open it in the browser. **Print those lines verbatim** (they give the file path and whether it opened) and do nothing else.
- If it is a **list**, the tracker has already rendered it as GitHub-flavored Markdown — two tables (Open then Closed) whose columns are a centered status glyph, then `#`/`Task`/`Category`/`Effort`/`Activity`, any "… older closed …" note, and a `**Commands**` section: an aligned command help block inside a ``` fence (command-and-description columns plus a `<n>` / `<n1, n2, …>` / `[N]` notation legend), not a bullet list or a table. **Print that block verbatim** to the user — do not re-transcribe it, rebuild the tables, renumber rows, reflow the aligned columns, or reword the commands. Do not take any other action.
- If it is a **task detail**, this session has just been attached to that task (reopened if it was closed). Do all of the following, in order:
  1. The terminal is tinted to the task's category automatically (full Sands palette via the hooks) — nothing to run by hand.
  2. Give the user a **detailed recap** — not a one-liner. Draw on the full summary and the recent-activity log:
     - State the overall **goal** in a sentence.
     - Break the summary's specific sub-items / acceptance criteria into a **bullet list** so nothing is buried.
     - Walk through what the **activity log** shows has happened so far, using its relative timestamps, so it's clear where the work left off and what the likely **next step** is.
  3. If the detail block includes a **resume command** (`cd … && claude --resume …`, or `cd … && claude --session-id …` when the task fresh-starts a clean session), surface it to the user **verbatim in a copyable code block** at the end of the recap, and explain it jumps straight back into the working session that holds this task's context (correct directory + session in one command).
  4. Ask what they'd like to do next, or just continue the work.

  Treat the digest as your authoritative context to continue; if a critical detail seems missing, the original working session's full transcript is one command away via `/todo <n> -s`.
  Treat this task as the active context for the rest of the session.
- If it is a **session-jump** (the block starts with `[SESSION-JUMP]` — produced by `/todo <n> -s`, which accepts a comma-separated list like `/todo 1,2,5 -s` to jump into several tasks at once), the user wants to hop **straight into each task's working session in a fresh window**, not read a recap. Each session-jump task is now attached (reopened if it was closed). The tracker has *already* tried to open a new Terminal window per task running its resume command, leaving this window untouched. The output may contain **several** `[SESSION-JUMP]` blocks — one per task. Do only this, then stop:
  - For **each** block that contains `[JUMP-WINDOW-OPENED]`: a new Terminal window is already up and running that task's resume command. Reply with **each** `↪ …` line from the block(s), one per task, copied verbatim, and nothing else — no preamble, no recap, no extra words. Do **not** run any resume command yourself; they're already running in the new windows.
  - For **each** block that does **not** contain `[JUMP-WINDOW-OPENED]` (auto-open failed, or there's no recorded session yet): surface that task's one-liner **verbatim in a copyable code block** — either `cd … && claude --resume …` (resuming the working session) or `cd … && claude --session-id …` (fresh-starting a clean, auto-attaching session when there's no valid session to resume) — so the user can run it themselves, note in one line what it does, and stop. Do not attempt to open a window yourself. (A `No task matching '…'.` line for a bad ref should be surfaced verbatim too.)

  Either way, **skip the recap** — that's the whole point of `-s`. Treat this task as the active context for the rest of the session.
- If the output starts with **`History —`** (`/todo <n> history`), the user asked for the task's **full trace** — the complete decisions log, the dated milestone log (`--log`), and the full activity log. **Print it verbatim** and do nothing else. It is **read-only**: it did NOT attach or reopen the task, so don't treat it as a resume. What history adds over the resume digest is the **retired** decisions plus the milestone and activity logs — the digest already shows every still-current decision, uncapped. Decisions here are **numbered**, and a retired one is shown marked `⊘ … — SUPERSEDED by decision <n>` (or `SPLIT into` / `MERGED into`); history stays complete, the digest drops them. Those numbers are what `update --supersedes <n>` / `--pin-decision <n>` take.
- If the output starts with **`# Prompts —`** (`/todo <n> prompts`), the user asked for the task's **exact prompt trail** — the chronological, timestamped, session-attributed list of the precise user prompts (and slash commands) that drove the task, oldest first (hub + every delegated worker; a worker brief is that worker session's first prompt). **Print it verbatim** and do nothing else. It is **read-only**: it did NOT attach or reopen the task. For the shareable Markdown version, point the user at `task-station prompts --task <n> --md`.
- If the output starts with **`[SAVE]`** (`/todo save`), the user wants to **checkpoint the current task for a seamless resume**. A save is an **AMENDMENT, not a rewrite**, and the block does not reprint the digest — you have been working this task, so you already have it. Work these steps in order. **(1)** Read the **GAP REPORT**: which named slots are EMPTY, which look STALE, what has landed since the last full checkpoint, and what the digest costs a fresh session (`/todo save --verbose` dumps the digest itself, for the rare session that genuinely lacks it). **(2)** Fill **only** what it named — leave an accurate slot alone. **(3)** Write the summary as **PRESENT TRUTH** with `--summary` (which **REPLACES** it wholesale): files/paths, branch/worktree/env, build-test-run commands, gotchas, open questions, and the user's most recent intent. Lean; never a history dump. The text it replaces is **preserved** — `update --restore-summary [n]` brings any version back. **(4)** Record this session's new choices with `--decision` + why (incl. approaches **tried & rejected**), adding `--supersedes <n>` when one replaces an earlier one (the number from `/todo <n> history`, repeatable) so the refuted one stops briefing future sessions, and `--pin` for a rule the rest of the work must obey (a pin is **reading order** — pinned decisions sort first, marked ★ — not survival; nothing current is ever hidden). **(5)** Append exactly **one** dated `--log` milestone. **(6)** Then the **COLD-READ CHECK**, which is mechanical: every named slot non-empty and `state` beginning with `NEXT:`. The stamping `update` reports any that fail and `/todo save --check` re-runs it; patch each with another `update`, then re-read the digest as if you have no memory of this conversation and patch anything ambiguous. **(7)** Confirm in one line. Note the block itself does **not** stamp a checkpoint — `last_full_save_ts` is written by the `update` carrying a `--summary` **and** a `--state` together, because that pair *is* the checkpoint. Do **NOT** pin a session or open/resume anything — `/todo save` only captures the digest (the full transcript of the working session stays recoverable via `/todo <n> -s` as a backstop).

- If the output starts with **`[HEAL]`** or **`[HEAL-SCAN]`** (`/todo heal`), the user wants to **reconcile** the task's append-only decision log into current state — the counterpart to `save`'s capture. `[HEAL-SCAN]` is the deterministic scan and changed nothing: print it verbatim and stop. For `[HEAL]`, work the block's judgment list with the three verbs — **supersede** what was refuted (`update --supersedes <n>`), **split** what is compound (add the atomic parts with `--decision`, then `heal --split <n> --into <n1,n2,…>`), and **merge** what is true but no longer load-bearing (add one summary decision, then `heal --merge <n1,n2,…> --into <n>`) — then retro-dispose any undispositioned acks and refresh a drifted `--state`. **Nothing is ever deleted**: each verb marks the original, drops it from the digest, and keeps it in `/todo <n> history` labelled with what replaced it (reversible via `update --restore-decision <n>`). Never touch the `--log` trail or `history`. A bare `/todo heal` is a **dry run**; `--apply` performs the mechanical plan after backing the task blob up. Confirm in one line what you reconciled.
- If the output starts with **`memo `**, **`Memo `**, **`Memos `**, or **`(no memos)`** (`/todo memo …`), the user sent, acked, or listed a **memo** — a fact/decision handed to a task's session(s) on a shared, visible ack ledger. **Print the result line(s) verbatim** and do nothing else.

**Memos awaiting your ack.** When a hook injects a `[task-station] N memo(s) awaiting YOUR ack on […]` block, another session handed this task a fact/decision. **Read the full body (`task-station memo show --task <n> --id <id8>`) and acknowledge it BEFORE acting** — the ledger shows which peers already handled it, so acking first is what stops two sessions from double-implementing the same change.

**An ack must say what it DID with the memo.** A bare ack is refused — an ack is a receipt, and treating a receipt as an integration is how a correction gets acknowledged and then never reaches the durable store that auto-loads next session. Pass **exactly one** disposition:

- `--decision [TEXT]` — promote it to a decision on this task (TEXT overrides the memo body)
- `--memory <slug>` — you folded it into that agent-memory note
- `--noop "<reason>"` — no durable change needed; the reason is **mandatory**

So: `… memo ack --task <n> --id <id8> --session <your-session-id> --decision 'the call + why'`. On the slash surface: `/todo memo ack <id8> <decision text>`, or `/todo memo ack <id8> memory:<slug>`, or `/todo memo ack <id8> noop:<reason>`. Because each memo needs its own disposition, **don't batch-ack** — work them one at a time.

A memo tagged **`[CORRECTS: …]`** declares what it replaces (a memory-note slug, `decision:<n>`, or another memo's id8). It **cannot** be acked without a disposition that engages that target — `--noop` is allowed but must be explicit. A memo tagged **`[reads as a correction]`** matched the correction-language backstop without declaring a target: treat it as one, and go update the durable store it contradicts.

Send a correction with `task-station memo send --task <n> --text '<body>' --corrects <memory-slug|decision:N|memo-id8>` (repeatable).

**Tracking & grouping (fold, don't fork).** Every topic is tracked from the first prompt — even a plain question becomes an `○ open` task (it auto-promotes to `● active` when work starts). Before creating a NEW task, scan the board (open + active): if the prompt continues an existing task, **attach to it and append the prompt as a note** (`attach --session <id> --task <ref> --note '<prompt>'`) rather than spawning a sibling — so related questions across sessions accumulate under one task. Only a genuinely new topic creates a task. A skipped session stays silent.

After any mutation (closing, attaching, creating, pinning, updating, or saving a task — including the `pin` / `done` / `config` / `save` action results from `/todo pin`, `/todo done`, `/todo config`, `/todo save`), surface the tool's result line(s) **verbatim** and do nothing else — do **not** re-render this full `/todo` list unless the user explicitly asks to see it.
